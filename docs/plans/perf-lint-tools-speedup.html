Plan: make lint-tools fast with identical findings

Context

In the SFS monorepo, bun lint-tools runs uncached and serially after turbo on every ci:lint: 24.8s measured on 2026-11-20 (unused service methods 17.3s, unused GraphQL 9.0s). Profiling on SFS apps/api (451 candidate members, 1,090 project files, 4,437 program files incl. 23.8 MB of node_modules declarations):

  • ts-morph Project load from tsconfig.json: ~2.1s for api, ~1.1s for portal-api. Each check loads its own, so this is paid twice per app.
  • findReferencesAsNodes() for each candidate member: ~6.5–8s total for api. Each call is a full language-service find-references: it text-scans every program file (including the Prisma client declarations, where names like create/update/findMany occur thousands of times) and resolves a symbol at each occurrence.
  • Prototype of the pre-pass below on SFS: proves all 451 api members and all 28 portal-api members used in ~2.2s / ~0.45s (including building the type checker), with no find-references fallback calls; dead set identical to the current algorithm.

Changes

1. Service methods: one direct-reference pass, find-references only as fallback

In src/find-unused-service-methods.ts, keep candidate selection exactly as today (@Injectable classes in **/*.service.ts; methods and properties; isCandidate unchanged: private, decorated, lifecycle hooks, dead-code-ignore-next-line, property initializer must be an arrow function or function expression; name must be an Identifier). Then:

  1. Collect all candidates of the app first (instead of deciding member by member). Map each candidate's declaration symbol (checker.getSymbolAtLocation(nameNode.compilerNode)) to the candidate, and collect the set of candidate names.
  2. Pre-pass: using the language service's program and type checker (project.getLanguageService().compilerObject.getProgram(), the same program find-references uses, so node/symbol bindings are shared), walk every program source file that is not a declaration file and not under /node_modules/ with raw ts.forEachChild (no ts-morph wrapping). For each PropertyAccessExpression whose name text is a candidate name, resolve checker.getSymbolAtLocation(name); if any of checker.getRootSymbols(symbol) is a candidate's symbol, mark that candidate used.
  3. Fallback: for each candidate not marked used, run the existing check unchanged (nameNode.findReferencesAsNodes(), filter out nameNode, dead if empty).
  4. Report in the same order and format as today (by file, then class, then member, in source order).

Why findings are identical by construction. The pre-pass only ever marks a member used; it never marks one dead. A member is reported dead only by the unchanged find-references call. So the pre-pass can change a finding only if it marks used a member that find-references would report unused. It cannot: for a property-access name, TypeScript's find-references (getReferencesAtLocation → getRelatedSymbol → forEachRelatedSymbol, checked in the bundled TypeScript of @ts-morph/common 0.28.1) resolves the same getSymbolAtLocation, takes getRootSymbols of it, and reports the location when a root symbol is in the search set, which always contains the member's own symbol. Such a location is never a definition, so ts-morph's findReferencesAsNodes yields it, and it is not the member's own name node. Find-references searches every program file, a superset of what the pre-pass scans. The root-symbol step matters: in SFS, call sites like this.managerService.update(…) resolve to a transient (instantiated) symbol whose root is the declared member; exact symbol identity proves only 33 of 451 members.

Anything the pre-pass does not cover (element access svc['m'], destructuring, object-literal / shorthand properties, calls through an interface or base class, unions without the member as a root, references only in declaration files) falls back to find-references, so behaviour there is unchanged and only the speed differs.

2. One ts-morph Project per API app, shared by both checks

Add a small memoized loader (one function, a Map keyed by tsConfigFilePath) in a new src/load-project.ts. Both find-unused-graphql.ts (which currently does new Project(...) after running the coverage) and find-unused-service-methods.ts call it. The GraphQL check only reads syntax; the service check later builds the type checker on the same Project. The check order and every console line stay the same; the Loading TypeScript project for … line stays printed by the service check even when the project is already loaded.

The cache lives for the CLI process (both checks run in one process from cli.ts), so both apps' projects stay in memory until exit. SFS api + portal-api fit comfortably; no eviction.

3. Docs

Update the header comment of find-unused-service-methods.ts to describe the pass + fallback. README wording ("via ts-morph reference analysis") stays accurate; no README change.
